# Simulink Model Drift Analyzer

> Context and architecture document for building a GitHub-native workflow that detects structural, interface, parameter, and behavioral drift between versions of Simulink `.slx` models.

## 1. Executive Summary

Simulink models stored as `.slx` files do not produce useful native Git text diffs. An SLX file is a compressed package that conforms to the Open Packaging Conventions standard and stores model information using UTF-8 XML and other formats.

The proposed solution extracts a stable, canonical representation of each model, compares two representations, evaluates the changes against configurable rules, and publishes the results through multiple adapters.

The recommended architecture is:

```text
SLX files
   |
   v
Extraction layer
   |
   v
Canonical model manifests
   |
   v
Semantic comparison engine
   |
   v
Drift manifest + rule findings
   |
   +--> Pull-request summary
   +--> SARIF 2.1.0
   +--> Workflow artifacts
   +--> Future dashboard or API
```

SARIF is not the primary representation of model changes. It is an optional adapter for actionable violations that should appear as GitHub code-scanning alerts.

The canonical JSON model manifest and drift manifest are the system of record.

---

## 2. Problem Statement

Git treats `.slx` files as binary artifacts and cannot provide a meaningful model-aware line diff.

Engineering teams need to answer questions such as:

- Were blocks added, removed, moved, or modified?
- Did a block parameter change?
- Did an input or output contract change?
- Did a signal type, dimension, unit, or sample time change?
- Did Stateflow logic change?
- Did model configuration change?
- Did requirement traceability change?
- Was a change only graphical, or could it affect behavior?
- Did generated code or simulation behavior change?
- Does the change violate an organizational policy?
- Can reviewers see the result directly in a pull request?

The solution must distinguish three concepts:

1. **Model evolution:** A factual description of what changed.
2. **Model drift:** A change from an expected baseline or approved contract.
3. **Policy violation:** A model change that violates an explicit rule.

Not every model change is an error. A new block may be intentional and should appear in the drift manifest, but it should produce a SARIF alert only if it violates a configured rule.

## 3. Verified Platform Facts

### 3.1 SLX packaging

MathWorks documents SLX as a compressed package conforming to the Open Packaging Conventions interoperability standard. It stores model information using Unicode UTF-8 XML and other international formats.

Source:

- https://www.mathworks.com/help/simulink/ug/save-models.html

### 3.2 Official Simulink comparison capability

MathWorks provides a Comparison Tool and a Three-Way Merge Tool for Simulink models. The Comparison Tool can compare models, visualize differences, export results, and support source-control workflows.

MathWorks also documents using Simulink model comparison in CI/CD workflows and attaching comparison reports to GitHub pull requests and GitLab merge requests.

Sources:

- https://www.mathworks.com/help/simulink/model-comparison.html
- https://www.mathworks.com/help/simulink/slref/comparisontool.html

### 3.3 Programmatic comparison results

MathWorks documents that comparison results can be saved as reports or MATLAB workspace variables.

Running:

```matlab
results = visdiff(modelname_A, modelname_B);
```

creates a `ModelDiffResults` object. The object includes information about the comparison, file names, filters, and hierarchical nodes that differ.

Source:

- https://www.mathworks.com/help/simulink/ug/exporting-printing-and-saving-comparison-results.html

### 3.4 SARIF

SARIF 2.1.0 is an OASIS standard for static-analysis tool output. It is a JSON-based interchange format.

GitHub accepts SARIF generated by third-party analysis tools and displays qualifying results as code-scanning alerts. GitHub supports a subset of the SARIF 2.1.0 schema.

SARIF is not exclusive to CodeQL. A third-party analyzer can generate SARIF and use GitHub's SARIF upload capability.

Sources:

- https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html
- https://docs.github.com/en/code-security/concepts/code-scanning/sarif-files
- https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/integrate-with-existing-tools/upload-sarif-file

### 3.5 SARIF identity and duplicate alerts

GitHub uses stable rule identifiers, paths, and fingerprints to associate findings across analysis runs. Inconsistent locations or identities can result in findings being treated as new alerts.

Source:

- https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support

## 4. Recommended Design Principles

### 4.1 Use official Simulink semantics where possible

The primary extractor should use supported MATLAB and Simulink APIs or official model-comparison results.

Avoid making undocumented SLX XML structures the public contract of the analyzer.

A raw-package extractor can still be useful for:

- Package integrity checks
- Inventory and diagnostics
- Metadata inspection
- Environments in which MATLAB is unavailable
- Detecting that the extractor encountered an unknown structure

It must not silently claim semantic equivalence when it cannot interpret part of a model.

### 4.2 Make the canonical manifest stable

The canonical schema should represent concepts such as blocks, ports, signals, parameters, and Stateflow elements. It should not mirror SLX XML element names or internal package paths.

This establishes an anti-corruption layer:

```text
SLX or Simulink release details
              |
              v
      Version-aware extractor
              |
              v
 Stable canonical model schema
```

If an SLX or Simulink release changes, only the extractor should need adaptation.

### 4.3 Make output deterministic

Two extractions of the same model must produce the same canonical JSON.

Canonicalization should define:

- Deterministic collection ordering
- Normalized model paths
- Normalized numeric and Boolean values
- Stable identities
- Exclusion of volatile timestamps and UI metadata
- Explicit representation of unavailable values
- Deterministic JSON serialization

### 4.4 Separate facts from policy

The comparison engine records factual changes.

The policy engine decides whether a change is acceptable.

Example:

```text
Fact:
VehicleSpeed changed from double to single.

Policy:
Changing a top-level interface data type requires approval.

Finding:
SIMULINK-IFACE-001, error.
```

### 4.5 Fail closed on incomplete analysis

An extractor failure must not produce an apparently successful analysis with zero drift.

The workflow should return one of these statuses:

```text
complete
partial
unsupported
failed
```

A partial, unsupported, or failed analysis should be visible in the pull request and workflow result.

## 6. Canonical Model Manifest

### 6.1 Design goals

The canonical model manifest should be:

- Independent of SLX package internals
- Deterministic
- JSON Schema validated
- Versioned
- Readable by humans and machines
- Suitable for graph reconstruction
- Suitable for structural hashing
- Explicit about extraction completeness

```json
    "name": "controller",

  "interfaces": {
    "inports": [],

    "charts": [],
```

```json
{
  "id": "block:controller/SpeedLoop/Gain",
  "path": "controller/SpeedLoop/Gain",
  "name": "Gain",
  "blockType": "Gain",
  "parent": "controller/SpeedLoop",
  "reference": null,
  "ports": {
    "inputs": 1,

  },
  "parameters": {
    "Gain": {
      "value": "2.5",
      "valueType": "expression"
    }
  }
}
```

### 6.4 Connection representation

```json
{
  "id": "connection:<stable-fingerprint>",
  "source": {
    "blockId": "block:controller/SpeedLoop/Integrator",
    "port": 1
  },
  "destination": {
    "blockId": "block:controller/SpeedLoop/Gain",
    "port": 1
  },
  "signal": {
    "name": "VehicleSpeed",
    "dataType": "double",
    "dimensions": [1],
    "unit": null
  }
}
```

### 6.5 Interface representation

```json
{
  "id": "interface:inport:VehicleSpeed",
  "name": "VehicleSpeed",
  "direction": "input",
  "port": 1,
  "dataType": "double",
  "dimensions": [1],
  "sampleTime": "inherited",
  "unit": "m/s",
  "minimum": null,
  "maximum": null
}
```

### 6.6 Stable identity

A block path is readable but may not remain stable after a rename or move.

The MVP can use normalized paths as identities while recording the limitation. A later version can implement matching using multiple signals:

- Persistent identifiers exposed by supported APIs, if available
- Normalized path
- Block type
- Parent system
- Neighboring connections
- Port signature
- Selected semantic parameters

Matching confidence can be included in a change:

```json
{
  "match": {
    "strategy": "path-and-signature",
    "confidence": 0.94
  }
}
```

A confidence value is analyzer output, not a value supplied by MathWorks.

## 7. Drift Manifest

The drift manifest describes all detected changes, including informational changes that should not become alerts.

```json
{
  "$schema": "./schema/drift-manifest.schema.json",
  "schemaVersion": "0.1.0",
  "comparison": {
    "baseArtifact": "controller-base.slx",
    "targetArtifact": "controller-head.slx",
    "status": "complete"
  },
  "summary": {
    "added": 2,
    "removed": 0,
    "modified": 3,
    "moved": 1,
    "interfaceChanges": 1
  },
  "changes": [
    {
      "changeId": "chg-<stable-hash>",
      "kind": "modified",
      "category": "interface",
      "elementType": "inport",
      "elementId": "interface:inport:VehicleSpeed",
      "modelPath": "controller/VehicleSpeed",
      "property": "dataType",
      "before": "double",
      "after": "single",
      "functionalClassification": "potentially-functional",
      "evidence": {
        "extractor": "simulink-api"
      }
    }
  ]
}
```

### 7.1 Suggested categories

```text
package
model
system
block
parameter
connection
interface
signal
stateflow
configuration
reference
requirement
generated-code
behavior
analysis
```

### 7.2 Suggested change kinds

```text
added
removed
modified
moved
renamed
reconnected
unresolved
unsupported
```

Do not infer `renamed` or `moved` unless matching evidence is strong enough. Otherwise, report a removal and addition.

## 8. Policy and Rule Model

Example rule configuration:

```yaml
rules:
  - id: SIMULINK-IFACE-001
    title: Top-level interface data type changed
    category: interface
    level: error
    match:
      elementType: inport
      property: dataType
      kind: modified

  - id: SIMULINK-STATEFLOW-001
    title: Stateflow transition removed
    category: stateflow
    level: warning
    match:
      elementType: transition
      kind: removed

  - id: SIMULINK-ANALYSIS-001
    title: Model analysis incomplete
    category: analysis
    level: error
    match:
      analysisStatus:
        - partial
        - unsupported
        - failed
```

The first release should use explicit rules rather than an opaque aggregate risk score.

If a risk score is introduced later, its weights and calculation must remain configurable and explainable.

## 9. SARIF Adapter

### 9.1 Appropriate SARIF content

Use SARIF for actionable, rule-driven findings such as:

- Prohibited interface changes
- Deleted required ports
- Incompatible signal contracts
- Prohibited configuration changes
- Missing required traceability
- Disallowed Stateflow changes
- Unsupported or incomplete analysis

Do not create SARIF alerts for every added block or layout change.

Those belong in the drift manifest and pull-request summary.

### 9.2 SARIF example

```json
{
  "version": "2.1.0",
  "$schema": "https://json.schemastore.org/sarif-2.1.0.json",
  "runs": [
    {
      "tool": {
        "driver": {
          "name": "Simulink Model Drift Analyzer",
          "version": "0.1.0",
          "informationUri": "https://github.com/example/simulink-model-drift",
          "rules": [
            {
              "id": "SIMULINK-IFACE-001",
              "name": "TopLevelInterfaceTypeChanged",
              "shortDescription": {
                "text": "A top-level interface data type changed"
              },
              "fullDescription": {
                "text": "Changing a top-level port data type can affect consumers of the model interface."
              },
              "defaultConfiguration": {
                "level": "error"
              }
            }
          ]
        }
      },
      "results": [
        {
          "ruleId": "SIMULINK-IFACE-001",
          "level": "error",
          "message": {
            "text": "VehicleSpeed changed from double to single."
          },
          "locations": [
            {
              "physicalLocation": {
                "artifactLocation": {
                  "uri": "models/controller.slx"
                }
              },
              "logicalLocations": [
                {
                  "fullyQualifiedName": "controller/VehicleSpeed",
                  "kind": "Simulink Inport"
                }
              ]
            }
          ],
          "partialFingerprints": {
            "modelDrift/v1": "<stable-fingerprint>"
          },
          "properties": {
            "modelPath": "controller/VehicleSpeed",
            "changeKind": "modified",
            "property": "dataType",
            "before": "double",
            "after": "single"
          }
        }
      ]
    }
  ]
}
```

### 9.3 SLX location limitation

An SLX element does not naturally map to a source-code line.

The SARIF adapter should therefore:

1. Point `artifactLocation.uri` to the `.slx` file.
2. Place the model path in `logicalLocations`.
3. Include model-specific data in `properties`.
4. Provide base and target values in the message or properties.
5. Optionally link to an HTML model-comparison report.

GitHub supports only a subset of SARIF 2.1.0. The adapter must be tested against GitHub's documented requirements rather than assuming every SARIF feature will be rendered.

### 9.4 Stable fingerprints

A proposed fingerprint input is:

```text
ruleId
+ repository-relative SLX path
+ normalized model element path or stable element identity
+ changed semantic property
```

Do not include:

- Commit SHA
- Workflow run ID
- Temporary extraction paths
- Timestamps
- Base or target values, unless a changed value must represent a distinct alert

This helps keep the same logical issue associated across workflow runs.

## 10. GitHub Actions Surface

The GitHub Action is the orchestration and enforcement surface, not the semantic database.

### 10.1 Proposed pull-request workflow

```text
Check out pull request
        |
Identify changed .slx files
        |
Obtain base and target versions
        |
Extract canonical manifests
        |
Validate manifests against JSON Schema
        |
Compare manifests
        |
Evaluate policy rules
        |
Generate:
  - model-drift.json
  - model-drift.md
  - model-drift.sarif
  - optional official comparison report
        |
Upload workflow artifacts
        |
Upload actionable SARIF findings
        |
Publish pull-request summary
        |
Set workflow conclusion
```

### 10.2 Conceptual workflow

Action versions should be pinned according to the repository's dependency and supply-chain policy before production use.

```yaml
name: Simulink model drift

on:
  pull_request:
    paths:
      - "**/*.slx"
      - "model-drift/**"

permissions:
  contents: read
  security-events: write

jobs:
  analyze:
    runs-on: ubuntu-latest

    steps:
      - name: Check out target revision
        uses: actions/checkout@<pinned-version>

      - name: Run model drift analyzer
        run: |
          ./model-drift analyze \
            --base-ref "${{ github.event.pull_request.base.sha }}" \
            --target-ref "${{ github.event.pull_request.head.sha }}" \
            --output build/model-drift

      - name: Upload analysis artifacts
        uses: actions/upload-artifact@<pinned-version>
        with:
          name: simulink-model-drift
          path: build/model-drift/

      - name: Upload actionable findings
        uses: github/codeql-action/upload-sarif@<pinned-version>
        with:
          sarif_file: build/model-drift/model-drift.sarif
          category: simulink-model-drift
```

This workflow is conceptual. The extraction step depends on the runner strategy, MATLAB availability, licensing, and implementation selected for the MVP.

### 10.3 Pull-request summary

```markdown

**Analysis:** Complete  
**Policy result:** Failed

### Model changes

- 2 blocks added
- 1 parameter changed

- **Warning:** Gain changed from `2.5` to `3.0`.

- Canonical target manifest

- Simulink comparison report
```

## 11. Extraction Strategies

### Strategy A: Supported Simulink APIs

Potential responsibilities include:

- Load the model
- Enumerate systems and blocks
- Read selected parameters
- Resolve ports and lines
- Inspect interfaces
- Inspect model references
- Inspect Stateflow content
- Record extraction diagnostics
- Close the model without changing the source artifact

Advantages:

- Semantic model access
- MathWorks owns SLX interpretation
- Less coupling to package internals

Trade-offs:

- MATLAB/Simulink runner and licensing requirements
- Release compatibility
- Potential execution of model callbacks or initialization logic
- Handling missing products or referenced artifacts

Security requirement:

Treat models from untrusted pull requests as potentially active content. Extraction should run in an isolated environment with restricted credentials and network access. The implementation must explicitly control whether callbacks, initialization scripts, referenced data, or custom code are executed.

### Strategy B: Official model-comparison output

Use documented comparison functionality as an authoritative or supporting comparison mechanism.

Advantages:

- Aligns with official model-diff semantics
- Produces reviewable comparison reports
- Supports CI/CD scenarios documented by MathWorks

Trade-offs:

- An adapter is still needed to transform comparison results into canonical changes
- Accessible properties must be verified against the supported MATLAB release
- SARIF still requires stable rules and identities

### Strategy C: Raw SLX package inspection

Advantages:

- Does not require a MATLAB runtime for basic inspection
- Useful for integrity checks and troubleshooting

Trade-offs:

- Undocumented internal XML should not become the stable application contract
- Semantics may be difficult to reconstruct
- Internal organization can vary
- Stateflow, references, and configuration may need specialized handling

### Recommended hybrid

```text
Primary semantic extraction:
    Supported Simulink APIs

Official comparison evidence:
    Comparison Tool / visdiff output

Fallback diagnostics:
    OPC package validation and inventory

Stable public contract:
    Canonical model and drift schemas
```

## 12. Compatibility and Validation Plan

### 12.1 Schema validation

Validate generated files against:

- `canonical-model.schema.json`
- `drift-manifest.schema.json`
- SARIF 2.1.0 schema
- GitHub's supported SARIF requirements

### 12.2 Golden models

Maintain small model fixtures that isolate change types:

```text
gain-parameter-change/
block-added/
block-removed/
block-moved/
port-type-change/
signal-reconnected/
stateflow-transition-added/
configuration-change/
referenced-model-change/
layout-only-change/
unsupported-feature/
```

Each fixture should contain an expected canonical manifest and drift manifest.

### 12.3 Release compatibility matrix

Test supported MATLAB/Simulink releases explicitly.

Record:

```text
Model saved by release
Extractor release
Load result
Extraction status
Canonical schema version
Expected drift result
Warnings
```

Do not claim broad cross-release support until demonstrated by tests.

### 12.4 Determinism tests

For every fixture:

1. Extract twice.
2. Serialize twice.
3. Compare bytes.
4. Assert identical hashes.
5. Verify that timestamps and temporary paths are absent.

### 12.5 Differential validation

Where possible, compare analyzer results with official Simulink comparison results.

A discrepancy should produce diagnostic output rather than being silently ignored.

## 13. Failure Modes

### Extraction failure

Response:

- Set analysis status to `failed`.
- Publish an analysis finding.
- Fail the workflow according to policy.
- Retain logs as an artifact.

### Unsupported model feature

Response:

- Set analysis status to `partial` or `unsupported`.
- Enumerate unsupported elements.
- Do not claim that no drift exists.
- Optionally block merging.

### Model callbacks or dependencies

A model may depend on initialization logic, dictionaries, libraries, referenced models, or custom code.

Response:

- Use an isolated environment.
- Restrict secrets and network access.
- Report missing dependencies.
- Record which references were resolved.
- Avoid evaluating unnecessary code.

### Unstable identifiers

Renames and moves may look like removal plus addition.

Response:

- Expose matching strategy and confidence.
- Begin with conservative matching.
- Never hide uncertainty.
- Preserve raw evidence for debugging.

### SARIF alert churn

Changing rule IDs, artifact paths, or fingerprints can reopen alerts.

Response:

- Version rule behavior deliberately.
- Keep rule IDs stable.
- Normalize repository-relative paths.
- Unit-test fingerprints.

### GitHub feature availability

GitHub code-scanning availability and permissions depend on repository type and enabled GitHub security features.

Response:

- Always keep JSON and Markdown outputs available.
- Make SARIF upload optional.
- Avoid making the core analyzer dependent on the GitHub alert UI.

## 18. Definition of Done for the First Prototype

The prototype is successful when it can:

1. Compare two versions of a controlled `.slx` test model.
2. Generate deterministic canonical JSON.
3. Detect an added block.
4. Detect a changed Gain parameter.
5. Detect a top-level port data-type change.
6. Produce a complete drift manifest.
7. Produce a readable pull-request summary.
8. Emit a valid SARIF finding for the interface violation.
9. Fail visibly when extraction is incomplete.
10. Preserve enough evidence to reproduce and troubleshoot the result.

## 20. Context for an AI Coding Assistant

When implementing this project:

- Do not parse undocumented SLX XML as the primary semantic API.
- Keep extraction, canonicalization, comparison, policy, and reporting as separate modules.
- Treat canonical JSON as the stable internal contract.
- Treat SARIF as an output adapter, not the source of truth.
- Never report "no drift" if extraction was partial or failed.
- Generate deterministic, schema-validated JSON.
- Keep rule IDs, repository paths, and SARIF fingerprints stable.
- Distinguish factual changes from policy violations.
- Treat `.slx` models and callbacks from pull requests as potentially untrusted.
- Prefer small golden fixtures and explicit expected outputs.
- Document every unsupported Simulink feature.
- Do not claim cross-release compatibility without fixture-based validation.
